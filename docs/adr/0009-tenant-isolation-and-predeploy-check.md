# 0009. 입주 격리와 배포 전 검사

상태: 확정 · 2026-11-24

## 배경

입주팀은 자기 레포의 compose로 배포한다. compose는 강력하다 — Docker 소켓을 마운트하거나
특권 모드를 켜면 서버 전체 권한을 얻는다. docker 그룹 계정도 사실상 root다.
"서버만 빌려준다"가 성립하려면 입주팀이 서버 자체를 건드릴 수 없어야 한다.

## 결정

**1. 입주팀에게 OS 계정을 주지 않는다.** 서버에 로그인하는 사람은 관리자뿐이다.
입주팀은 Komodo에서 자기 스택에 대해 실행(Execute)·로그·터미널 권한만 갖는다.
스택 설정(환경 변수 등) 변경은 관리자에게 요청한다.

**2. 프로젝트 단위로 나눈다.** Docker 네트워크, 포트 대역, CPU·메모리 상한.

**3. 배포 전에 compose를 검사한다.** Komodo 스택의 `pre_deploy` 훅에서 `policy/`의 검사
스크립트를 실행하고, 아래에 걸리면 배포를 중단한다.

| 거부 항목 | 이유 |
|---|---|
| `privileged: true`, 위험한 `cap_add` | 호스트 권한 획득 |
| `network_mode: host`, `pid: host` | 다른 프로젝트·호스트와의 격리 무력화 |
| Docker 소켓 마운트 | 서버 전체 제어 |
| 스택 폴더 밖 bind mount | 호스트·다른 프로젝트 파일 접근 |
| 배정 대역 밖 포트 공개 | 접근 규칙 우회 |
| 자원 상한 없음 | 한 프로젝트가 서버를 독점 |

**4. 예외는 코드로 남긴다.** `tenants/<프로젝트>/policy.yml`에 구체 항목과 사유를 적고 PR로 승인한다.
Docker 소켓, 특권 모드, 대역 밖 포트는 예외로도 허용하지 않는다. 포트가 모자라면 대역을 늘린다
(접근 규칙이 대역 단위라, 대역 밖 포트는 소유 팀이 못 쓰거나 다른 팀에게 열린다).

## 결과

- 규칙이 문서가 아니라 실행되는 검사다. 시험 파일(통과/거부 예시)로 검사 자체를 검증한다.
- 비용: 입주팀이 환경 변수 하나를 바꿀 때도 관리자를 거친다. 프로젝트가 늘면 병목이 될 수 있다.

## 확인이 필요한 것

`pre_deploy` 훅이 실패하면 Komodo가 배포를 실제로 멈추는지는 아직 시험하지 않았다.
Komodo 구축 시 **가장 먼저** 시험한다. 멈추지 않으면 이 결정을 다시 검토한다.

## 검토한 대안

- rootless Docker / 프로젝트별 VM: 격리는 더 강하지만 운영 부담이 크다. 입주팀이 늘면 재검토.
- 문서로만 규칙 안내: 지켜지는지 확인할 방법이 없다.

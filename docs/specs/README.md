# 작업 명세

구현 세션의 입력. **명세 한 장 = PR 하나 = 이슈 하나.**
이슈는 명세 링크와 진행 상태만 담는다. 내용은 여기에만 쓴다.

## 목록

| 번호 | 제목 | 상태 | 먼저 끝나야 하는 것 |
|---|---|---|---|
| 0-xx | 현재 구조의 급한 보완 | 비공개 | — |
| [1-01](1-01-ansible-skeleton.md) | 새 Ansible 뼈대 | 대기 | — |
| [1-02](1-02-vault-and-password.md) | vault 이전과 비밀번호 자동화 | 대기 (결정 필요) | 1-01 |
| [1-03](1-03-ci-gates.md) | CI 검증 확장 | 대기 | 1-01 |
| [1-04](1-04-predeploy-policy-check.md) | 배포 전 검사 스크립트 | 대기 | — |

2단계(fender) 이후의 명세는 그 단계에 들어갈 때 쓴다. 미리 쓰면 그때쯤 낡는다.

0단계는 아직 고치지 않은 문제를 다루므로 비공개로 관리한다.
명세 파일은 **수정과 같은 PR**에 넣어 공개한다.

## 형식

```markdown
# <번호> <제목>

상태: 대기 | 진행 | 완료 · 마일스톤: <단계>

## 목적          한두 문장. 왜 하는가.
## 범위 밖       하지 않는 것. 구현 세션이 넓히지 않도록.
## 완료 조건      번호 목록. 각 항목 = 실행할 검사 + 기대 결과.
## 전환과 되돌리기  서비스를 끊지 않는 순서, 실패하면 어떻게 되돌리나.
## 참고          관련 ADR, 폴더의 AGENTS.md
```

## 완료 조건 쓰는 법

테스트를 믿을 수 있어야 "통과 = 완료"가 성립한다.

- **관찰 가능한 결과**로 쓴다. "설정을 넣었다"(✗) → "외부에서 요청하면 401이 온다"(✓)
- **검사하는 위치를 적는다.** 서버 안에서 본 결과와 밖에서 본 결과는 다르다.
- **구현 전에 실패해야 한다.** 고치기 전에도 통과하는 검사는 아무것도 증명하지 않는다.
- 서버를 바꾸는 명세에는 다음 둘을 항상 넣는다.
  - 두 번째 적용에서 변경 0건 (`changed=0`, 또는 plan에 변경 없음)
  - 전환 전후로 운영 중인 서비스가 응답함
- 2단계 이후의 명세에는 장애 시험을 넣는다: 해당 서버를 끈 상태에서 나머지가
  [ADR 0011](../adr/0011-failure-blast-radius.md)의 표대로 동작한다.
- 검사는 `ansible/verify/<번호>.yml` 또는 한 줄 명령으로 실행 가능해야 한다.

## 규칙

- 완료 조건은 사용자가 승인한 것이다. **구현 세션은 고치지 않는다.**
  틀렸거나 달성할 수 없으면 멈추고 묻는다.
- 명세에 없는 일은 하지 않는다. 발견한 문제는 이슈로 남긴다.
- 끝나면 이 표의 상태와 `docs/architecture.md`의 상태표를 같은 PR에서 갱신한다.
- 한 장은 70줄 이하. 넘으면 명세를 둘로 나눈다.
